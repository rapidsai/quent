<objective>
Add per-thread identity to the Phase-1 capture vocabulary so the Phase-2 analyzer can
reconstruct Push/Pop ranges as per-thread nested stacks (ANA-03). Today `RangePush`/`RangePop`
carry only `domain` and the injection layer discards the calling thread before emit
(RESEARCH §Open Question #1, D-17). This plan stamps `thread_id: u32` (Linux OS thread id, the
same id space `NameThread` uses) onto `RangePush`/`RangePop` at capture time.

Scope decision (planner, per D-17 "your call on Mark/RangeStart"): add `thread_id` to
`RangePush`/`RangePop` ONLY (2 variants — the minimal blast radius D-17 sanctions). `Mark` and
`RangeStart` are NOT extended: ANA-04 matches Start/End process-wide by `range_id` (thread-
independent) and marks group by domain; named-thread grouping of marks/start-end ranges is a
Phase-3 nicety not required by any Phase-2 requirement, so it is deferred to keep the capture
change narrow.

Purpose: unblock ANA-03 (per-thread Push/Pop reconstruction) which is otherwise unsatisfiable
for multi-threaded producers (libcudf/cuCascade).
Output: `RangePush`/`RangePop` carry a real OS thread id end-to-end (capture → event → stream).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| NVTX C caller → injection callback | Foreign library invokes `extern "C"` callbacks; a panic must never unwind across the ABI. |
| crates.io → build | One new third-party crate (`libc`) enters the supply chain. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-SC | Tampering | `libc` crate install | mitigate | Blocking human legitimacy gate (Task 1) verifies `rust-lang/libc` on crates.io before add. |
| T-02-01A | Denial of Service | Push/Pop callbacks reading thread id | mitigate | Thread-id read stays inside the existing `catch_unwind` guard; no new panic path across the C ABI. |
| T-02-02A | Information Disclosure | OS thread id in captured events | accept | `gettid` is a process-local kernel id, not sensitive; already conceptually exposed via `NameThread`. |
</threat_model>
